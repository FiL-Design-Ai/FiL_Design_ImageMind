### 2.1. НАЙДЕН И ПОЧИНЕН: обрезанный ответ выдавался за готовый

Это главная находка аудита. Пак портил результат своей основной функции, и ни один из 1060 тестов
этого не видел.

**Как обнаружилось.** В живом прогоне Google вернул `Red circle, green square, blue` — без
«triangle». Повторил с двумя бюджетами:

```
max_tokens=200  -> 'Red circle, green'                        (17 символов, оборвано)
max_tokens=1000 -> 'Red circle, green square, blue triangle.' (40 символов, целое)
```

**Причина.** `common/models.py`, обе стратегии разбора ответа. Код выглядел так:

```python
if content:
    return content          # ← выход отсюда, ничего больше не проверив
if finish_reason == "length":
    raise TruncatedAnswerError(...)
```

Проверка «модель оборвали на полуслове» стояла **после** возврата текста, поэтому срабатывала
только когда текста не было совсем. Стоило модели успеть сказать хоть что-то — обрывок уходил
дальше как законченный ответ. У пака есть ровно тот механизм, который должен это чинить
(`TruncatedAnswerError` + лестница бюджетов `_budget_ladder`), он просто никогда не запускался в
этом случае.

**Насколько плохо.** На модели с «размышлениями» — хуже, чем просто обрезка. Groq при
`max_tokens=300` вернул 1130 символов внутреннего монолога, оборванного на полуслове, так и не
дойдя до ответа. Дальше `common/clean_output.py:56` снимает незакрытый тег `<think>` — и наружу
выходит рассуждение модели вместо промпта:

```
'The user wants me to identify shapes. Let me look carefully. - Top left: Red circle - Top right: Green squa'
```

Это уходит прямо в генератор изображений.

**Починка.** `common/models.py` — признак обрыва проверяется **до** выдачи текста, в обеих
стратегиях (OpenAI-совместимой и Google). Обрезанный ответ теперь поднимается на ту же лестницу
бюджетов, что и пустой; на исключении едет и сам обрывок, чтобы лог мог сказать, сколько успело
прийти. Нода показывает исход читаемым сообщением — 🕵️ Optic Scanner ловит `FiLError`
(`nodes/node_scanner.py:493`) и пишет «Ошибка: …» вместо падения.

**Проверка починки — на живом провайдере, тот же вызов:**

```
[GOOGLE] 'gemini-3.6-flash' was cut off at 200 tokens (spent 8, 29 chars produced); retrying at 2000.
max_tokens=200 -> 'Red circle, green square, blue triangle.'
```

Полный набор тестов после правки: **1060 прошло, 0 упало** — ровно столько же, сколько до неё.
Это и есть иллюстрация проблемы: набор был зелёным и с багом, и без него.

## Фаза 3. Фронтенд

### 3.1. НАЙДЕНО И ПОЧИНЕНО: `^` в числовом поле считал не то

`FilNumberInput.vue` — поле, которое умеет считать выражения вроде `1024+64`. В его собственном
комментарии написано: «and the literal `^` as `**`», то есть `^` должен работать как возведение в
степень.

Не работал. Код проверял одну строку, а вычислял другую:

```js
if (!/^[0-9+\-*/(). ]+$/.test(cleaned.replace(/\^/g, "**"))) return null;  // проверяем 2**10
const fn = new Function(`"use strict"; return (${cleaned});`);            // вычисляем 2^10
```

Замена `^` на `**` делалась **только для проверки**. В `new Function` уходила исходная строка, а в
JavaScript `^` — это побитовое исключающее ИЛИ. Итог: `2^10` давало **8** вместо 1024. Молча, в поле,
которым задают размеры изображения.

**Починено:** замена делается один раз, до проверки, и дальше и проверяется, и вычисляется одна и та
же строка.

Заодно проверил, что фильтр входа безопасен: регулярка пропускает только цифры, пробелы и
`+ - * / ( ) .` — букв нет, значит из выражения не дотянуться ни до одного имени в области
видимости. Это в порядке.

**Тестов на этот виджет не было ни одного.** Для поля, которое прогоняет ввод через `new Function`,
это худшее место для нулевого покрытия. Написал 13 тестов: арифметика, `^`, отказ от нечисловых
выражений, деление на ноль, зажим в диапазон, шаги стрелками и с Shift, откат по Esc, коммит по
Enter и по потере фокуса, синхронизация с внешним значением.

### 3.2. НАЙДЕНО И ПОЧИНЕНО: единственный патч без защиты от повторного применения

`nodes2/applyFxComposables.ts` дописывает `onConnect`/`onDisconnect` в прототип класса ноды — и
делает это без проверки, не сделано ли уже. Вызывается из всех 15 нод.

Что это значит: `beforeRegisterNodeDef` не обязан выполниться ровно один раз — обновление
определений нод его повторяет. При втором проходе в цепочке остаётся две копии обёртки, и эффект
подключения срабатывает дважды на каждое соединение.

- **`FilSelect` не переписывает значение, которого нет в списке.** Проверил отдельно: воркфлоу,

### 4.1. Установлен ровно тот ComfyUI, на котором пак ломался

### 4.1. Установлен ровно тот ComfyUI, на котором пак ломался

В `python_embeded` стоит **comfyui_frontend_package 1.47.10** — та самая версия, которую
`nodes2/host/heightModel.ts:70-75` называет причиной, по которой запись `widget.height` бросала
исключение внутри цикла отрисовки LiteGraph, и **все ноды пака рисовались пустыми**.

Проверил по самому бандлу хоста, а не по комментарию. В `1.47.10` пять геттеров `height` и **только у
одного есть сеттер** — и это не виджет, а класс размерной пары (`get height(){return this[3]}` /
`set height(e){this[3]=e}`). Без сеттера остались, в частности:

```
get height(){return this._height}                              ← BaseWidget
get height(){return this.computedHeight||super.height}          ← DOM-виджет
get height(){return Q.NODE_TITLE_HEIGHT+this.bodyHeight}        ← нода
```

**Вывод:** проверка `isWritable()` в `heightModel.ts:76` — не запас на будущее, а несущая конструкция
прямо сейчас, на этой машине. Уберут её — все 15 нод перестанут рисоваться.

### 4.2. Канал, через который пак задаёт высоту, хостом действительно читается

Пак публикует высоту, подменяя `widget.computeSize()`, и комментарий утверждает, что это
«поддерживаемый канал, который LiteGraph и читает». Проверил — так и есть. В бандле 1.47.10 высота
виджета берётся так:

```
computedHeight ?? e.computeSize?.(c)[1] ?? NODE_WIDGET_HEIGHT
```

То есть `computeSize()` читается, когда хост не проставил свой `computedHeight`. Утверждение
подтверждено по коду хоста.

### 4.3. НАЙДЕНО И ПОЧИНЕНО: smoke-набор нельзя было запустить на машине разработчика

Самая неприятная находка фазы, потому что она объясняет, почему дефекты стыка доезжают до
пользователя.

`npm run test:smoke` — единственная проверка, которая поднимает **настоящую** ComfyUI и смотрит, что
пак в ней регистрируется и рисуется. Локально она падала, не дойдя до первого теста:

```
ModuleNotFoundError: No module named 'sqlalchemy'
Error: Process from config.webServer was not able to start. Exit code: 1
```

Причина — `playwright.comfy.config.ts:39` жёстко звал `python main.py`. В CI это верно: workflow
ставит зависимости ComfyUI в интерпретатор раннера. На портативной сборке — а `ComfyUI-Easy-Install`
именно такая — это неверно: зависимости лежат в `python_embeded`, а системный `python` про них не
знает. Проверил оба:

```
python_embeded\python.exe -c "import sqlalchemy"  ->  2.0.48
системный python                                  ->  ModuleNotFoundError
```

**Почему это важно.** Набор был зелёным в CI и неработающим локально. То есть проверить стык с хостом
на той машине, где стоит ComfyUI 1.47.10 — версия, под которую этот стык и написан (см. 4.1), — было
нельзя. Проверка существовала, но не была доступна там, где нужнее всего.

**Починено:** интерпретатор берётся из `COMFY_PYTHON`, по образцу уже имеющегося в этом же файле
`COMFY_URL`; умолчание `python` оставлено, чтобы CI не менялся.

```
COMFY_PYTHON=E:\AI\ComfyUI-Easy-Install\python_embeded\python.exe npm run test:smoke
```

Второй путь, который тоже работает: запустить ComfyUI самому — `reuseExistingServer` направит набор
на то, что уже слушает порт.

### 5.1. Секреты не были исключены из публикуемого архива

артефактов тестов.

### 5.2. Счётчик нод в сканере конфликтов врал

`tools/scan_node_conflicts.py` рапортовал «none of our **13** ids collide», когда нод 15 — в
захардкоженном `OUR_IDS` не было `FiLSignalSwitch` и `FiLDatasetForge`.

**Поправка к первоначальной оценке:** дыры в обнаружении нет. Сам поиск конфликтов идёт по имени
папки пака, а не по этому списку, и всегда покрывал все 15 нод. `OUR_IDS` использовался ровно в
одной строке — в счётчике. Но цифра, показывающая меньше нод, чем есть, читается как пропуск в
проверке, а список продолжал бы отставать с каждой новой нодой.

**Починено:** список вычисляется из собственных исходников пака. Сканер теперь говорит «our 15 ids».

### 5.3. Контроль качества кода: решение отложено

Разбор в 0.1 показал, что `.pre-commit-config.yaml` не запускается нигде и не проходит вручную.

себе содержательные изменения этого аудита.

**Не тронуто намеренно.** Вынесено отдельным пунктом в «Что осталось».
